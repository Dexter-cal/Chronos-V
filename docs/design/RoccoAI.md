# Rocco AI (Meta-Agent) Design Document

## 1. Overview

Rocco AI is the meta-agent and central nervous system of the ChronoVerse engine. It is not a typical AI module that performs a single task, but rather a supervisor AI that orchestrates the other AI modules to ensure a coherent, consistent, and high-quality gameplay experience. Rocco is the "director" of the AI ensemble.

## 2. Core Responsibilities

### 2.1. AI Orchestration and Supervision
- **Goal-oriented task execution:** Rocco will take high-level goals (e.g., "generate a new region for the player", "create a new quest for the player") and break them down into a sequence of tasks for the other AI modules.
- **Example workflow for "generate a new quest":**
  1. Rocco asks the **Narrative AI** to generate a quest concept.
  2. Rocco asks the **World Builder AI** to ensure the necessary locations for the quest exist or to create them.
  3. Rocco asks the **NPC AI** to assign the quest to a suitable NPC and generate the initial dialogue.
  4. Rocco asks the **Physics AI** to verify that the quest objectives are physically possible.
- **Dynamic task re-ordering:** Rocco will be able to dynamically re-order or modify the task sequence based on the results from the other AI modules.

### 2.2. Coherence and Consistency Management
- **Cross-module validation:** Rocco will be responsible for validating the outputs of the AI modules against each other to ensure coherence. For example, it will check if the dialogue generated by the NPC AI is consistent with the lore from the Narrative AI.
- **Maintaining the "World State":** Rocco will maintain a high-level understanding of the current state of the game world, including the story, the player's progress, and the state of key NPCs and locations. This "World State" will be used to ensure that all AI-generated content is contextually appropriate.

### 2.3. Conflict Resolution
- **Mediating between AI modules:** If two AI modules produce conflicting outputs (e.g., the World Builder AI wants to place a mountain where the Narrative AI has placed a city), Rocco will resolve the conflict.
- **Resolution strategies:**
  - **Priority-based:** Rocco can have a predefined hierarchy of AI modules.
  - **Negotiation:** Rocco can ask one or both modules to revise their output.
  - **Creative synthesis:** Rocco could attempt to synthesize a creative solution that satisfies both modules (e.g., "place the city on the mountain").

### 2.4. Quality Control
- **Evaluating AI-generated content:** Rocco will have a set of heuristics or a dedicated "Quality AI" model to evaluate the quality of the content generated by the other modules.
- **Requesting revisions:** If the quality of the generated content is too low, Rocco will ask the responsible AI module to revise it.

## 3. Integration

Rocco is the central hub and will integrate with almost all other AI modules. It will be the primary client of the other AI modules' APIs.

## 4. Future Enhancements

- **Learning from player feedback:** Rocco could learn to improve its orchestration and conflict resolution strategies based on player feedback (e.g., if players consistently get stuck on a certain type of quest, Rocco could learn to generate them differently).
- **Predictive orchestration:** Rocco could use the Predictive AI to anticipate the player's actions and proactively generate content for the upcoming scenes.

## 5. Communication Protocol

Rocco AI will communicate with the other AI modules within the orchestrator using a direct, function-call-based protocol. This is a simple and efficient approach for a monolithic orchestrator where all modules are part of the same application.

### 5.1. Rocco to other AI modules
- **Mechanism:** Rocco will import the necessary processing functions from the other AI modules (e.g., `process_physics_query` from `physics_ai.py`).
- **Data Format:** Rocco will call these functions directly, passing the appropriate request model (e.g., `PhysicsQueryRequest`) as an argument.
- **Example:**
  ```python
  from .physics_ai import process_physics_query, PhysicsQueryRequest

  # Rocco constructs a request
  request = PhysicsQueryRequest(query_type="is_area_clear", parameters={"x": 10, "y": 20})
  # Rocco calls the Physics AI's function
  response = process_physics_query(request)
  ```

### 5.2. Other AI modules to Rocco
- **Mechanism:** The other AI modules will not call Rocco directly. They will simply return a response to Rocco's function call. This maintains a clear, hierarchical control flow with Rocco at the top.
- **Data Format:** The response will be an instance of the appropriate response model (e.g., `PhysicsQueryResponse`).

### 5.3. Future Enhancements: Event-Driven Architecture
- For future scalability, especially if we move to a microservices architecture where each AI module runs as a separate service, we can transition to an event-driven communication protocol.
- **Mechanism:** Rocco and the other AI modules would communicate by publishing and subscribing to events on a message bus (e.g., RabbitMQ, Kafka).
- **Benefits:** This would decouple the AI modules, making the system more resilient and scalable. However, for the initial implementation, the direct function-call approach is sufficient.

## 6. Internal API Design

This section defines the internal API that Rocco will use to interact with the other AI modules. This API is based on the direct function-call protocol defined in the previous section.

### 6.1. Narrative AI Interface
- **Function:** `process_narrative_request(request: NarrativeRequest) -> NarrativeResponse`
- **Purpose:** To handle all requests to the Narrative AI, such as generating quest concepts, dialogue, and lore.
- **`NarrativeRequest` model:** Will contain fields like `request_type` ("generate_quest", "generate_dialogue") and context-specific parameters.

### 6.2. World Builder AI Interface
- **Function:** `process_world_builder_request(request: WorldBuilderRequest) -> WorldBuilderResponse`
- **Purpose:** To handle all requests to the World Builder AI, such as creating or verifying locations.
- **`WorldBuilderRequest` model:** Will contain fields like `request_type` ("create_location", "verify_location") and parameters like `location_type` and `coordinates`.

### 6.3. NPC AI Interface
- **Function:** `process_npc_request(request: NPCRequest) -> NPCResponse`
- **Purpose:** To handle all requests to the NPC AI, such as assigning a quest to an NPC or updating an NPC's state.
- **`NPCRequest` model:** Will contain fields like `request_type` ("assign_quest", "update_state") and parameters like `npc_id` and `quest_data`.

### 6.4. Physics AI Interface
- **Function:** `process_physics_query(request: PhysicsQueryRequest) -> PhysicsQueryResponse`
- **Purpose:** To handle all physics queries, as designed in the Physics AI module.
- **Models:** Uses the `PhysicsQueryRequest` and `PhysicsQueryResponse` models already designed.

### 6.5. Animation AI Interface
- **Function:** `process_animation_request(request: AnimationRequest) -> AnimationResponse`
- **Purpose:** To handle all animation generation requests, as designed in the Animation AI module.
- **Models:** Uses the `AnimationRequest` and `AnimationResponse` models already designed.

### 6.6. Generic Interface Structure
- This API design follows a consistent pattern:
  - Each AI module has a single entry point function (e.g., `process_<module_name>_request`).
  - Each module has its own set of Pydantic models for requests and responses.
- This structure makes the API clean, consistent, and easy to extend as new AI modules are added.
